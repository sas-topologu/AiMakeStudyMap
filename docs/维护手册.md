# AI点星谱 · 维护手册

> 版本 v1.1（适配知识卡 v2.0 教材标准与前端动效）。面向维护者（人类或 AI）的系统架构说明与维护操作手册。部署与日常运行见《部署运行指南》。

## 1. 架构总览

前后端分离，单进程交付：

```
浏览器（Vue3 SPA + Canvas 星图）
   │  HTTP/JSON，JWT 鉴权
   ▼
Node.js + Express（server/）── 静态托管 web/dist（生产模式）
   │  better-sqlite3（WAL）
   ▼
SQLite 单文件库（server/data/starmap.db）
   ▲  导入/校验/扫描（content/tools/）
content/cards/（知识卡 JSON 源文件，内容的唯一事实来源）
```

- **节点数据库**（静态、版本化）：nodes / edges / questions / meta / changelogs 表。内容只经导入工具写入，**不要直接手改库中内容**。
- **用户数据库**（动态、高频）：users / user_node_state / daily_usage / posts / replies / creations / pioneers / shares / corrections / search_logs 表。节点状态、跃迁额度、计时防沉迷全部在服务端判定与落库，前端无判定权。
- **本地缓存**：客户端 localStorage 缓存卡片与邻域，按 `content_version` 差异同步。
- **内容资产**：卡片引用的图片/动画存于 `content/assets/`，经 `GET /api/assets/<相对路径>` 提供（防目录穿越、白名单扩展名 svg/png/jpg/jpeg/gif/webp、immutable 长缓存）。

### 3.0 前端随机性设计（2026-08-13 优化）

- **粒子系统**：`ParticleSystem` 构造/`setEmblems` 用 `randomSeed()`（时间戳⊕熵）重置 PRNG → 每次进入节点星星序列全新；传 `seed` 可复现（测试用）。PRNG 统一用 `macroLayout.mulberry32`。
- **背景星空**：`canvasBase._makeStars` 幂律分层（85% 小/12% 中/3% 大星），每颗星带 `twPhase/twSpeed`，`drawBackground` 用 `performance.now()` 做呼吸闪烁（0.72~1.0）。仅在渲染循环运行时可见（静止零开销）。
- **特效中心点**：`emblemOffsets.js` 的 `pickEmblemOffsets(renderer, centerId, count, salt)` 用 `mulberry32(hashStr(centerId) ^ 会话盐)` → 同一会话内反复进入同一节点位置稳定不跳变；刷新页面（盐变化）重新随机。避开邻节点（NODE_CLASH=90）与组间互距（GROUP_GAP=135）。
- **宏观宇宙视图**：`MapView.startTwinkle` 低功耗 rAF（仅宇宙模式 + 页面可见 + 非 reduced-motion），星系星云/星光呼吸闪烁；进入星座视图/页面隐藏自动停止。
- **试卷抽题**：`quizService.pickQuestions` 按题型轮询随机抽取（多题型时每类至少 1 道，避免全抽同一题型），不足时随机补足。

## 3. 核心业务规则速查

| 规则 | 实现位置 | 参数 |
|---|---|---|
| 状态机 dim→open→passed→lit | stateService.js | open = 显式存储或任一相连节点 passed/lit 推导 |
| 闯关 3 题全对→通关 | quizService.js | pass 模式固定 3 题 |
| 考核全对→点亮 | quizService.js | 题数 min(clamp(22−4×难度,4,20), 题库容量) |
| 闯关须先开计时，不可取消 | timerService.js | 到时提交一律拒绝 |
| 防沉迷日限 2 小时 | timerService.js | daily_usage 当日累计 >120 分钟拒绝新开计时 |
| 跃迁扣额 | routes/jump.js | 目标 dim 扣 1 点转 open；月赠 1、上限 2 |
| 讨论区限流 | routes/posts.js | meta `post_rate_threshold`（默认 100 帖+回复/小时/节点），≥阈值 429 |
| 高难节点 | navService.js | meta `hard_min_attempts`（默认 5）、`hard_max_pass_rate`（默认 0.3）：尝试≥5 且通过率<0.3 判高难 |
| 拓荒者 | pioneerService.js | 点亮时节点点亮人数 <10，30 分钟后仍 <10 → 永久标记；懒提升 + 每分钟兜底 |
| 速通榜 | routes/posts.js 等 | pass_seconds 升序；前 10 发言带角标并排序优先 |

修改阈值的方法：直接改 meta 表对应行（如 `UPDATE meta SET value='50' WHERE key='post_rate_threshold';`），无需改代码。

## 4. 内容维护流程

### 4.1 新增/修改知识卡（AI 维护主流程）

按《知识卡制作规范》§10 执行：staging → `--check --with-db` 校验 → 审核 → 移入 cards → `npm run import`（自动迭代 content_version 并写更新日志）。客户端基于版本号自动增量同步。**卡片引用本地图片/动画时，须同步把文件放入 `content/assets/`（按 `节点id首段/文件名` 组织）**，导入工具会校验文件存在，缺失即中止。

### 4.2 勘误流程

```
用户提交（节点页"勘误"按钮）→ corrections 表 pending → /admin 审核
  ├─ 采纳（可附备注）→ 成为待办任务 → 维护者改源卡 → npm run import → 版本迭代
  └─ 驳回（可附备注）→ 用户在"我的勘误"可见结果
```

注意：采纳**不会**自动改卡，合并动作永远是"改 content/cards 源卡 + 导入"，保证源文件是内容的唯一事实来源。

### 4.3 二创审核

用户在节点页上传（需点亮该节点）→ pending → `/admin` 通过/拒绝。通过后展示在节点二创区。

### 4.4 定期维护扫描

```bash
npm run scan        # 输出维护报告
```

报告分区：结构健康（节点/边/题数、环检测、学科分布）、孤岛检测、空洞节点（近 7 天 ≥3 次搜索无结果的词——新卡选题信号）、待办积压（pending 勘误/二创）、版本信息。建议每次内容迭代前后各跑一次。AI 维护流程以本报告为输入：孤岛 → 补关联或补中间卡；空洞词 → 评估是否制卡。

## 5. 常见维护操作

- **调整限流/高难阈值**：改 meta 表（见 §3）。
- **补录/修订更新日志**：admin 调用 `POST /api/admin/changelog {version, summary, detail}`（同版本 upsert）。
- **提升某用户为管理员**：`UPDATE users SET is_admin=1 WHERE username='...';`（首个注册用户自动为 admin）。
- **重置某用户某节点状态**：删除 `user_node_state` 对应行即可（open 推导不受影响）。
- **删除节点**：目前导入工具不清理已从 cards 移除的节点。确需删除：从 cards 移除源文件后，手动删除 nodes 行及其 edges/questions/user_node_state 关联行，再 `UPDATE meta SET value=value+1 WHERE key='content_version'` 并补一条 changelog。操作前务必备份数据库。
- **数据库直接查看**：`node -e "const db=require('better-sqlite3')('server/data/starmap.db');console.log(db.prepare('SELECT id,title FROM nodes').all())"`（或任何 SQLite GUI）。

## 7. 安全要点

- 生产环境**必须**设置 `STARMAP_SECRET`（JWT 密钥），不要使用默认 `dev-secret`。
- 所有状态流转（通关/点亮/跃迁扣额/计时）均在服务端校验，前端篡改无效——新增涉及状态的功能时遵守同一原则。
- 用户输入统一 zod 校验；正文 Markdown 渲染前端已做 XSS 转义，新增富文本展示位时复用 `utils/markdown.js`，不要直接 `v-html` 原始内容。
- 密码 bcryptjs 哈希；JWT 有效期 7 天。
