# 概念模型：个人端 与 群体端

> **本文件是全项目唯一的术语基准。**
> 任何文档、界面文案、代码注释、对外说明，提到"端"的时候只能使用本文的两个词：**个人端**、**群体端**。
> 旧说法（客户端 / 用户端 / 前端 / 服务端 / 后台 / 本地端 / 云端 / 终端 / 单机版 / 在线版）一律废弃，见 §5 对照表。

---

## 1. 一句话

- **个人端**：属于你一个人的完整学习工具 —— **功能全都有，谁都别管我。**
- **群体端**：大家共用的一份知识库和一块公共场地 —— **只存不管，多一件事都不做。**

整个项目只有这两样东西。剩下的所有说法，都只是这两样东西在不同场合的别名。

---

## 2. 怎么判断一个东西属于哪一边

只问一个问题：**这份数据的主人是「一个人」还是「一群人」？**

- 主人是一个人 → 个人端
- 主人是一群人 → 群体端

**不看的三个东西**：

| 不看的 | 为什么 |
|---|---|
| 跑在哪台机器上（本机 / 公网 / 云主机） | 位置不改变归属 |
| 怎么打开的（网页 / 安装包 / 手机 App） | 外形不改变归属 |
| 连没连网（单机 / 在线） | 形态不改变归属 |

> 反过来说：**"云端"不是一种端**，只是群体端常见的摆放位置；**"单机版"不是一种端**，只是个人端一种常见的运行形态。

---

## 3. 两侧分别是什么

### 3.1 个人端（Personal）

**是什么**：你一个人的知识库 + 你一个人的学习工具。库里有什么、你学到哪、错了什么题，全在这里，全归你。

**原则：全功能、少限制。**

**全功能** —— 下面这些必须能在个人端独立完成，**群体端不在场、断网、群体端关掉，都要能用**：

| 类别 | 内容 |
|---|---|
| 看 | 星图浏览、节点详情、搜索 |
| 学 | 学习、闯关、考核、刷题 |
| 记 | 进度、错题、复习队列、最近学习 |
| 管自己 | 计时、目标 |
| 造 | 制卡、导入、导出、备份、本地 AI 制卡 |
| 看自己 | 进度统计、学习成果 |
| 调 | 外观、特效、界面微调 |

**少限制** —— 个人端不给自己加锁：

- 不强制登录才能看、才能学（登录只为区分"这是谁的数据"）
- 不强制联网；**断网时功能一个都不能少**
- 不做防沉迷、不做时长上限、不做额度门槛；若要保留这类约束，必须是**可配置、可一键关掉**的
- 不为了"防作弊"牺牲可用性：个人端的主人就是这份数据的主人，判分、状态这类判断放在个人端就够

**两种形态**：

- 只有个人端（不连任何群体端）= 过去叫"单机版"
- 个人端 + 连上某个群体端 = 过去叫"在线版"

**数据**：存在个人端自己的库里。可以随时导出成一个文件、备份、换机器、送人。

### 3.2 群体端（Collective）

**是什么**：一群人共用的一份知识库 + 一块公共场地。它的主人是这群人，不是某个人。

**原则：只提供必要服务，尽量降低自己的权限和功能。**

**只做三件事**：

1. **仓库**：存知识库、对外分发、收投稿、审稿入库、版本与变更记录
2. **社区**：讨论、二创、分享托管、榜单 / 纪念碑这类公共协作
3. **盖章**：给**它当场见证过**的成果盖一个「已认证」章（见 §4）—— 只标好的，不标差的

**明确不做的事**（做了就是越权、就是多余）：

- 不判分、不判对错、不记任何人的**私人**学习进度（只保管"已提交给群体展示"的那部分记录）
- 不计时、不管额度、不管时长
- 不做个人学习统计、不评价谁努力
- 不读个人端的本地数据
- **不给用户贴任何负面标签**：没有"低可信 / 未验证 / 存疑 / 待核实"这种东西，也不据此区分对待
- **不拦截、不否决、不回退、不删改**个人端上传的成果；不接受就不接收，接受了就照单收下
- 不追求功能多：能少一个功能就少一个

**权限最小化**：

- 群体端的界面只有"管理公共库"所必需的东西
- 管理员分两级，原则是**够用就行、越小越好**（具体见 `docs/维护手册.md`）

**形态**：跑在一台长期在线的机器上（公网服务器或局域网主机），被动提供服务。

## 4. 成果与认证：个人做，群体盖章

这是全模型里**唯一一处个人端与群体端真正交接**的地方，也是冲突的解法定式。

### 4.1 冲突是什么

个人端要"全功能、断网也能用"，那么很多成果是**离线产生**的；可成果一旦要挂到社区里展示，别人就会问：**这是真的吗？**

群体端**无法验证离线发生的事**——除非限制用户必须联网才能学，而那正好违反个人端的"全功能、少限制"。

### 4.2 解法：不设门槛，只盖「已认证」章

群体端**不阻止任何上传**，也**不给任何人贴负面标签**。它只做一件事：给**它当场见证过**的成果盖一个**认证**章。

| 状态 | 怎么产生 | 例子 | 怎么显示 |
|---|---|---|---|
| **已认证** ✔ | **必须联网**，由群体端当场见证 | **点亮**（lit） | 带「已认证」标记 |
| 未认证 | 个人端本地完成（含断网） | **通关**（passed）、刷题、复习记录 | 普通展示面**不做任何标记**；**不进榜单** |

**只标好的，不标差的。**

- 没有"低可信 / 未验证 / 存疑 / 待核实"这一类的说法和标记 —— 那是对用户的不尊重。
- **未认证不等于可疑**，只是"群体端当时不在场"。未认证的成果与已认证的**平等展示、平等可用**：不降权、不隐藏、不折叠、不提示、不比较。
- 个人端**永远**不因为断网而少任何功能。
- 个人端联网后把本地成果**上报**给群体端；群体端**一律接收**，只负责盖认证章。
- 群体端**可以在用户联网时监管**：见证、抽查、事后核验；核验通过就**补上**认证章。
  - 监管的手段**只有补章**：没有禁止、没有删除、没有回退、没有公开指责。

### 4.3 认证章怎么用

| 场合 | 收不收未认证 |
|---|---|
| **榜单类**：速通榜、拓荒者（前十名额 + 纪念碑） | **只收已认证** —— 服务端直接过滤，未认证的不出现在榜上 |
| 普通展示：个人进度、讨论区、二创、个人主页 | **一视同仁**：照常展示、不降权、不隐藏、不做任何标记 |

- 未认证的成果**不会因为不上榜而失效**：进度照算、后续节点照样解锁、错题照常入列。
- 榜单只认已认证，是因为它比的是"谁先谁后"；没被库当场见证过的成绩，不该去占稀缺名额。
- 除了"上榜 / 不上榜"这一条，两者在别处没有任何区别，也**不给用户任何提示或压力**。

> **别和"内容状态"搞混**：知识卡本身另有一个**内容状态**（验证通过 / 存在争议 / 待审核），评的是**卡片内容**、不是人；它与本节讲的「认证」是两回事，用词也已明确分开 —— 「可信度」这个词不再使用。

### 4.4 一句话记住

> **个人端说了算，群体端只能盖认证章，不能管人。**
> 群体端可以"看"，可以"盖"，不可以"管"，更不可以"贬"。

### 4.5 落到代码上的含义（尚未实现，见 §9）

- **判分已下放到个人端**：个人端缓存题库（随 `/sync` 一并发下），断网时本地出卷、本地判分（`web/src/utils/localQuiz.js`，与库侧同规则）。联网时仍走库判分 —— 那是"已认证"的那条路。
- **点亮保持联网见证**，所以它天然"已认证"；离线时个人端明确提示"点亮需要联网完成"。现有的拓荒者 / 速通榜逻辑本来就建立在服务内核的点亮计数上，方向是对的。
- **成果上报**已落地（`POST /api/achievements`）：个人端启动时与恢复联网时各补报一次；库一律接收、只升不降、节点不存在就跳过。
- 成果记录只需要一个 `certified` 字段（已认证 / 未认证）；**不要**设计"可信度分级"，更不要在界面上出现任何负面标记。
  - 已落地：`user_node_state.certified`（默认 1 = 走接口即库在场），写入时取 `MAX` 保证**只补不撤**。
  - 展示面：**榜单类只收已认证**（速通榜按 `s.certified = 1` 过滤；拓荒者名额判定 `litCount` 也只算已认证；纪念碑只列已认证）；普通展示面两者一视同仁。
- 单机形态（只有个人端，没有群体端）下没有社区可言，**认证不参与任何判断**，不打搅用户。

## 5. 旧说法 → 新说法

| 旧说法 | 归为 | 说明 |
|---|---|---|
| 客户端、用户端、前端、网页端 | 个人端 | 都只是"一个人用的那一面" |
| 本地端、本机 | 个人端 | 位置不改变归属 |
| 单机版 | 个人端（独立形态） | 不连群体端的个人端 |
| 服务端、后台 | 群体端 | 服务于一群人 |
| 云端 | 群体端（部署位置） | "云"是位置，不是角色 |
| 终端 | **废弃** | 过去既指个人端的库、又指群体端的服务，是混乱的主要来源 |
| 管理端 | 个人端管理 / 群体端管理 | 两侧都有"管理"，管的范围不同，见 §6 |

## 6. 一处必须分清的地方：两种"管理"

"管理"要分两半，过去混在一起才显得管理界面重复：

| | 个人端管理 | 群体端管理 |
|---|---|---|
| 管什么 | **我自己的库**：允许的文件格式、我的备份、我的导入导出、投向我小库的内容 | **公共库**：公共投稿审核、举报、勘误、社区秩序、认证盖章 |
| 谁能进 | 我就是主人 | 群体管理员（分级） |
| 目的 | 让工具顺手 | 让公共内容可信 |

> **同一个功能落在哪一侧，取决于库的主人是谁。**
> 例：同样叫"审核投稿"——审核进自己小库的投稿，是个人端管理；审核进公共库的投稿，是群体端管理。

## 7. 两侧的关系

```
        ┌──────────────┐  拉取知识库 / 提交投稿 / 参与社区 / 上报成果   ┌──────────────┐
        │    个人端     │ ─────────────────────────────────────────▶ │    群体端     │
        │  （我的工具） │ ◀───────────────────────────────────────── │  （大家的库） │
        └──────────────┘        下载已公开的知识库 + 认证标记          └──────────────┘
              ▲                                                            ▲
              │ 可选、可随时断开；断网时功能一个都不少                       │ 被动等待连接
              └── 不连也完全可用                                            └── 只收、只盖认证、不管
```

- 一个群体端可以服务很多个人端。
- 一个个人端可以连很多群体端（换个库就是换个学习范围）。
- **个人端不依赖群体端**：不连、断网、群体端关掉，个人端照常用。

## 8. 代码与目录怎么对应

> 目录名暂不改（改名成本高、收益低），但**含义按本文理解**。

| 目录 | 在新模型里是什么 |
|---|---|
| `web/` | 个人端的界面 |
| `server/` | **服务内核**：个人端与群体端共用同一套代码。跑在个人机器上、只服务一个人 = 个人端的库；跑在公网、服务一群人 = 群体端 |
| `desktop/` | 个人端的桌面形态（内嵌服务内核，库在本地） |
| `mobile/` | 个人端的手机形态（只做界面，连个人端或群体端） |
| `content/` | 知识库内容与制卡工具（个人端和仓库都用） |
| `tools/` | 运维与自动化脚本（哪一侧需要就放哪一侧） |

**关键点**：`server/` 不等于"群体端"。它是一套服务内核，**归属由主人决定** —— 这是 §2 那条判断规则的直接结果。单机版里内嵌的那部分仍然属于个人端，因为它只服务一个人。
